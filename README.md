# Brrvrvvt Lulin Daniil
1.В первом случае главное — не правило iptables, а то, на каком адресе слушает сам сервис. SSH слушает только 127.0.0.1:22, поэтому подключиться к нему снаружи через 203.0.113.10:22 нельзя: внешний интерфейс не связан с этим SSH-сокетом. Правило ACCEPT dpt:22 лишь разрешает проход пакетов через firewall, но не заставляет SSH принимать соединения на внешнем адресе. Поэтому привязка сервиса к адресу здесь важнее правила firewall. 
2. Для выхода web42ns в интернет одного veth и адреса 10.200.0.2 недостаточно. В namespace должен быть маршрут по умолчанию через адрес хоста, на хосте должен быть включён IP forwarding, а также нужен MASQUERADE, чтобы приватный адрес 10.200.0.2 заменялся внешним адресом хоста. Тогда пакет идёт из web42ns на хост, хост делает NAT и отправляет его в интернет, а ответы через NAT возвращаются обратно в namespace. Без этого web42ns может общаться с хостом, но в интернет не выйдет. 3. Порт 8080, опубликованный Docker через -p 8080:8080, не обязан попадать в цепочку INPUT. Docker перехватывает такой пакет в PREROUTING, делает DNAT и отправляет его к контейнеру через цепочку FORWARD. Поэтому ufw deny 8080 в INPUT не блокирует этот трафик: пакет до INPUT вообще не доходит. То есть схема примерно такая: интернет → PREROUTING → Docker DNAT → FORWARD → web-42:8080. 
4. Reverse proxy лучше тем, что наружу можно оставить открытыми только 80/443, а сам web-42:8080 не выставлять напрямую в интернет. Кроме того, nginx может принимать HTTPS и заниматься сертификатами, направлять разные домены или пути к разным контейнерам, выполнять авторизацию и ограничение запросов. При прямом открытии 8080 приложение становится непосредственно доступным извне, а все эти функции пришлось бы решать отдельно.
